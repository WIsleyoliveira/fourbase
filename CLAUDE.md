# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev        # runs API (:3001) + Vite (:5173) concurrently, with hot reload on the frontend
npm run dev:api     # API only (node server.js) — no hot reload, restart manually after backend edits
npm run dev:web     # Vite only
npm run build        # production build to dist/
npm run preview      # preview the production build
npm start             # node server.js (single-process, used by `vercel dev` / production-style run)
npm test              # node:test — tests/*.test.js (API against a temp local DB, no network; the mailer's fetch is injected, nothing is sent)
```

Tests use the built-in `node:test` runner, no extra framework. `tests/workspace-isolation.test.js` boots the Express app against a throwaway `FOURBASE_DB_PATH` fixture with two workspaces and asserts no cross-tenant reads/writes and correct gestor/funcionário gating — run it after touching any route's `workspace_id`/`user_id` filters. `tests/workspace-isolation-extra.test.js` covers the remaining mutating routes (todos, media, columns, folders and their documents, report activities, member/invitation removal); `tests/auth-rate-limit.test.js` is its own file because the login limiter (20 failed attempts per 15 min per IP, successful logins do not count) keeps per-process state. There is no lint config.

The Vite dev server proxies `/api/*` to `http://localhost:3001` (see `vite.config.js`) — always hit the frontend through `:5173`, not `:3001` directly, so the proxy and cookies/headers behave like production.

## Architecture

### API layout
`api/index.js` is only the entry point: builds the Express app (helmet, CORS, JSON, rate limit on credential routes) and mounts one router per domain from `api/_lib/routes/*.js` (auth & invitations, profile, tasks, notifications, members, notes, todos, media, folders, columns, tags, team, clients, reports). Routers register full `/api/...` paths and are mounted without a prefix. Shared pieces live in `api/_lib/`: `supabase.js` (DB client), `auth.js` (JWT, `auth`/`gestorOnly` middleware, `workspaceOf`, `authLimiter`), `http.js` (`asyncRoute`, `appOrigin` — invite links only), `validation.js` (`inWorkspace`, `validMemberIds`, `normalizeColor`, `isUuid`), plus the notification modules below. The `_` prefix matters: Vercel turns every non-underscored file under `api/` into its own serverless function — keep new backend modules under `api/_lib/`.

### Data backend: real Supabase in production, local mock in dev
With `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` set (production on Vercel), the API (`api/_lib/supabase.js`) uses the real Supabase Postgres with the **service_role** key. All `fourbase_*`/`weflow_*` tables have RLS enabled with **no policies** (migration `20261002000000_lock_down_table_rls.sql`), so the anon key shipped in the browser bundle cannot touch them — the Express API is the only path to the data, and it enforces tenancy by filtering every query on `workspace_id` from the JWT. Never add a permissive table policy back, and never expose the service_role key to the frontend (`VITE_*`).

Without `SUPABASE_URL` (default local dev), `api/_lib/supabase.js` falls back to the local mock instead. It imports `createLocalClient()` from `api/localDb.js`, a hand-rolled shim that implements the subset of the `supabase-js` query-builder chain this codebase actually uses (`.from().select().eq().in().order().single().maybeSingle().insert().update().delete().upsert()`). The object it returns is "thenable" (works with `await` and inside `Promise.all`), so route handlers are written exactly as if `supabase` were the real client — swapping backends means changing one line.

Data is persisted to `data/db.json` (gitignored), created and seeded on first run: one gestor account (`gestor@fourbase.com` / `gestor123`), 3 demo clients, and the 3 default Kanban columns. Delete that file to reset to a clean seed.

Known gap in the shim: it does **not** parse embedded-resource/join select syntax (`col:table!fk_name(...)`). The one route that needed a join (`GET /api/team/tasks`) resolves it manually — fetches tasks and users separately and merges them in JS. Follow that pattern rather than teaching the shim to parse joins.

The mock file path can be overridden with `FOURBASE_DB_PATH` (used by the tests). The SQL schema for that path (tables, columns, RLS policies) is tracked in `supabase/migrations/*.sql` — the local shim doesn't enforce any of this, so keep those files in sync when you add a field to a table used by both paths. The local file-based DB does **not** work on Vercel (no persistent disk across serverless invocations) — a real deploy needs the Supabase client restored.

Frontend file uploads (`src/supabase.js`) are a separate concern and still go straight from the browser to real Supabase **Storage** buckets (`fourbase-media`, `fourbase-client-media`), bypassing the Express API entirely to avoid serverless payload limits. Data lives in the local mock; file blobs live in real Supabase Storage — don't conflate the two when debugging uploads vs. data persistence.

### Auth
Custom JWT auth (not Supabase Auth). `POST /api/auth/login|register` sign a JWT containing `{sub, name, role}`; the `auth` Express middleware in `api/_lib/auth.js` only verifies the signature — it never re-checks that the user id still exists in the DB. Consequence worth knowing: a browser tab holding an old token will keep "succeeding" even after `data/db.json` is deleted/reseeded, silently writing rows under a `user_id`/`assigned_to` that no longer matches anyone. If data looks like it's "disappearing" for one browser tab but not others, suspect a stale token before suspecting the DB — log out and back in to get a token bound to the current seed.

Two roles: `funcionario` (only sees their own tasks/notes — `GET /api/tasks` filters `assigned_to = req.user.id` server-side) and `gestor` (single seeded account; gated routes via the `gestorOnly` middleware — member management, `/api/team/*`). Client-side, `gestorOnly`-flagged entries in the `VIEWS` array in `App.jsx` hide whole nav tabs (e.g. "Equipe") from non-gestor users; this is UI convenience only, the real enforcement is server-side.

### Routing and state: URL-driven navigation; server data lives in TanStack Query
Navigation uses react-router-dom (`BrowserRouter` in `src/main.jsx`). **All server data lives in TanStack Query** (`QueryClientProvider` in `main.jsx`, defaults in `src/queryClient.js`): tasks, notes, clients, tags, columns, members, folders — see the sections below. **`App.jsx` holds no domain data**: only the session, navigation (URL → screen), layout (sidebar, topbar), the profile/onboarding handlers and the "send to Kanban" modal; it uses `useClients()` solely to resolve the client open in the URL. Each screen reads what it needs straight from the hooks in `src/hooks/` — **do not add domain state or props-drilling to `App.jsx`**; add a hook instead. First-load spinners belong to the screen (`LoadingBlock` + `anyLoading`, wrapper pattern: a thin default export shows the spinner, the real body is a separate component). The URL is the source of truth for navigation: `src/routes.js` (pure functions, unit-tested in `tests/routes.test.js`) parses the location into `{view, clientId, tab, activationToken, taskId}` (`taskId` comes from `?tarefa=<id>`, valid on any screen; `withTaskParam(search, taskId)` sets/removes it), and `App.jsx` derives `view`/`selectedClientId`/`clientTab` from it — never keep them in `useState`; change them with `navigate(viewPath(...))` / `navigate(clientPath(id, tab))`. Routes: `/painel /kanban /calendario /notas /clientes /relatorios /cadastro /equipe /perfil`, `/clientes/:id[?aba=docs]`, `/activate/:token`. Unknown URLs, gestor-only screens opened by a funcionário, and `/clientes/:id` of a client that doesn't exist all redirect (replace) to a valid screen. A new top-level screen needs an entry in `VIEW_KEYS` (and `GESTOR_ONLY_VIEWS` if restricted) plus the `VIEWS` array; `vercel.json` already rewrites every non-`/api` path to `index.html`. Screens that still fetch with `useEffect` + `src/api.js` (DocumentsView folders/files, TeamView, ReportsView activities, ProfileView) are the next candidates for hooks; prefer a hook over a new `useEffect` fetch.

### Tasks (TanStack Query)
One collection, four cached views, all under the `['tasks']` key prefix (`TASK_KEYS` in `src/taskCache.js`): `mine` (assigned to me — Kanban, Painel; key includes the user id), `by-client/:id` (client Kanban, all assignees, polls every 6 s), `client-linked` (Calendário, polls 15 s while that screen is open) and `client-stats` (progress on the client list, an object not a list). Queries/mutations are in `src/hooks/useTasks.js`. **Every task screen reads the cache itself**: Calendário and Painel (`useMyTasks`/`useClientLinkedTasks`/`useTaskActions`), the personal Kanban (`MyKanban`, exported from `Kanban.jsx`) and the client workspace (`useClientTasks`). `Kanban` itself is the shared board: it takes only `tasks`, `clients` (the client workspace passes `[client]` to scope the form's client selector), `currentUser` and `onAdd` (the client workspace's `onAdd` pins new tasks to its client); members, columns, tags and the move/update/delete/add-column/create-tag actions come from hooks inside it.

Mutations (`useTaskActions`) are optimistic across **every** cached list at once (`patchAllTaskLists`): snapshot → patch → request → on failure restore the snapshot, toast, invalidate. Never hand-sync a task into several lists, and never add a task state in `useState` — add a query key under `['tasks']` instead (a list is anything under that prefix except `client-stats`). Created tasks go into the lists they belong to via `addTaskToLists`; `forceMine` keeps the old behavior that a task created from your own Kanban/Calendário shows up immediately even if assigned to someone else (it disappears on the next refetch — a known quirk, not a feature). `logout` calls `queryClient.clear()`; polling pauses while the browser tab is hidden (TanStack default), so to test it in a headless/background tab fake `document.visibilityState`. Pure cache logic is tested in `tests/taskCache.test.js`.

### Notes (TanStack Query)
One list per user under `NOTE_KEYS.mine(userId)` (`src/noteCache.js`, pure helpers tested in `tests/noteCache.test.js`); `src/hooks/useNotes.js` has `useNotes()` (user id comes from the session, no props) and `useNoteActions()` (create/save/delete/link folder/attachments, toasts included). **Notas, Painel and Documentações all read this same list** — `DocumentsView` used to keep its own copy and hand-sync it; never reintroduce a local `notes` state. Delete and (un)link-to-folder are optimistic with rollback; create/save/attachments wait for the server's version. `saveNote` returns `true/false` so the editor only clears "unsaved changes" when the save really succeeded. `NotesView` is a thin wrapper (spinner on first load, then mounts `NotesWorkspace`) because the editor picks the open note once on mount (incl. the one coming from Documentações via `targetNoteId`).

### Clients, tags, columns and members (TanStack Query)
`src/hooks/useWorkspaceData.js`: `useClients`/`useClientActions`, `useTags`/`useTagActions`, `useColumns`/`useColumnActions`, `useMembers`/`useMemberActions` (invite) + `patchMemberInCache` (a saved profile updates the member list without refetching); keys `['clients'|'tags'|'columns', userId]`. Calendário, Painel, Relatórios, Clientes, Cadastro and Notas call them directly (no props). Clients: create/update wait for the server and **rethrow** (the modals show the error); delete is optimistic with rollback and, on success, invalidates `['tasks']` and `['folders']` (Postgres `on delete set null` clears the tasks' `client_id`; the local mock DB does not simulate that). The "unknown `/clientes/:id`" redirect in `App` waits on `clientsQuery.isPending`. Columns: `useColumns` paints instantly from `localStorage` (`fb_cols_<userId>`) or `DEFAULT_COLUMNS` (`initialData` + `initialDataUpdatedAt: 0`, so it still revalidates on mount) — pure helpers in `src/columnCache.js`, tested in `tests/columnCache.test.js`; `addColumn` is optimistic and rolls back with a toast if the API refuses (no more "ghost" columns). "Recarregar dados" runs `queryClient.invalidateQueries()` (everything).

### Toasts and shared hooks
`src/toast.jsx` provides `ToastProvider` (wrapped in `main.jsx`) and `useToast()` → `{showToast, handleError}` (stable functions). Use it anywhere — hooks and screens — instead of threading `onError`/`onToast` props. Other cached resources follow the same pattern as tasks: `src/hooks/useFolders.js` (`['folders']`, `staleTime: 0`, so screens revalidate on open; only the Painel uses it so far). `App` has no global spinner: each screen shows its own `LoadingBlock` until the data it reads arrives (see the routing section), so Kanban/Painel never flash empty.

### Client-scoped workspace pattern
Opening a client in `ClientsView` navigates to `/clientes/:id`; `App.jsx` then renders `ClientWorkspace` instead of the client list — a Kanban + Documentos tabs UI scoped to that one client, via the `client_id` foreign key present on both `fourbase_tasks` and `fourbase_folders`. Any new client-scoped feature should hang off `ClientWorkspace` rather than introducing a new top-level view (its URL is `/clientes/:id`, sub-tab in `?aba=`).

### Notifications (bell + e-mail)
In-app bell and immediate e-mail for four kinds: `mention` and `assignment` (bell + e-mail), `due_soon` and `overdue` (bell only). Table `fourbase_notifications` (+ `users.notify_email boolean default true`) lives in `supabase/migrations/20261003000000_notifications.sql`: RLS on, no policies, unique partial index `(user_id, dedupe_key)`; the local shim registers it in `WORKSPACE_SCOPED`/`TIMESTAMPED`/`UNIQUE_COLUMNS` (and gained `.is()` and `.limit()`). A user without `notify_email` (pre-migration) counts as on.

**Backend modules (`api/_lib/`):**
- `notificationRules.js` — pure, no DB: `diffTaskNotifications(before, after, actorId, activeIds)`, `dueNotifications(tasks, today)`, `resolveToday` (accepts the browser's `?today=` only within ±1 day of the server date), `canViewTask`, `addDays`. The actor is never notified; someone who got `assignment` in the same action gets no `mention`; inactive members are skipped; edits that change neither assignee nor mentions emit nothing.
- `notifications.js` — `emitTaskNotifications(before, after, actor)` writes the bell rows and fires the e-mails; **it never throws** (errors are logged, the task save is unaffected). It is called from `POST /api/tasks` (before = `null`) and `PATCH /api/tasks/:id` in `routes/tasks.js`; PATCH reads the "before" row only when the body has `assigned_to` or `mentioned_users`. **This is the single emission seam — future webhooks (sub-project C) must plug in here**, no generic events table. Also `materializeDueNotifications`, `listNotifications`, `markRead`, `markAllRead` (these *do* throw → 500).
- `mailer.js` — `sendMail` (Resend via `fetch`, 4 s timeout, never throws, returns true/false), `buildNotificationEmail` (plain text, task title as text), `runInBackground` (`waitUntil` from `@vercel/functions`, so the response doesn't wait). Without `RESEND_API_KEY` it logs the e-mail and sends nothing.
- `routes/notifications.js` — `GET /api/notifications?today=AAAA-MM-DD` → `{items, unread}`, `PATCH /api/notifications/:id/read` (204; 404 if not the caller's or not a UUID), `POST /api/notifications/read-all` (204). Every query filters on `user_id` **and** `workspace_id` from the JWT.
- `GET /api/tasks/:id` (in `routes/tasks.js`) — allowed for gestor, assignee, mentioned user, or any member when the task has a `client_id`; everything else (missing, other workspace, no access, non-UUID id without querying) is the same 404. **Keep it registered after** `/api/tasks/by-client/:clientId`, `/client-linked` and `/client-stats` or it swallows them.

**Due notifications have no scheduler.** They are materialized when `GET /api/notifications` is read (the bell polls every 30 s): `due_soon` for due today/tomorrow, `overdue` for up to 7 days late (reference date = `due_date_end || due_date`), one row per (task, due date) through `dedupe_key` (`kind:<task>:<due>`; the unique index drops repeats, so rescheduling allows a new notice). A due row is hidden from the list when the task is done/deleted/reassigned, or when `meta.due_date` no longer equals the task's current due date. The list reads a bounded window — the user's 200 most recent rows, filtered, first 50 returned — and `unread` counts unread rows **inside that window** (real Supabase caps at 1000 rows; there is no cleanup job).

**E-mail rules.** Only for mention and assignment, to members that are active, have an address and `notify_email !== false`; at most one e-mail per (recipient, task, kind) per 10 minutes — the throttle looks at that user's notification rows (same task + kind) created in the last 10 minutes, not at actual sends (the bell row is always created); plus a cap of `MAX_EMAILS_PER_HOUR` = 20 e-mails per recipient per rolling hour, counted from that user's `mention`/`assignment` rows (rows created while `APP_URL` was unset or `notify_email` off also count) — over the cap the e-mail is skipped with a `console.warn`, the bell row still exists. `buildNotificationEmail` truncates the task title to 120 characters and the actor name to 60 (ellipsis, after whitespace collapsing). The link is `APP_URL/painel?tarefa=<id>` and the origin comes **only** from `process.env.APP_URL` — never from the request `Origin`/`Host` (phishing hardening). With `APP_URL` unset no e-mail is sent (the bell still works) and a console warning is logged. Resend only delivers to the account owner's address until a sending domain is verified.

**Frontend.** `src/hooks/useNotifications.js` (`['notifications', userId]`, 30 s polling, sends the local `today`, optimistic `markRead`/`markAllRead` with rollback + toast; pure cache helpers in `src/notificationCache.js`), `src/notificationText.js` (texts; author name from `useMembers()`, fallback "Alguém"), `NotificationBell` (desktop `.topbar` and `.mobile-topbar`; click marks read and navigates to `?tarefa=<id>` keeping the current screen). `?tarefa=<id>` is parsed by `src/routes.js` and rendered in `App` by `TaskPeekModal`: a read-only portal overlay (Esc/close removes the param with `replace`; "Tarefa não encontrada" on 404) backed by `useTask(id)` (key `['task', id]`, outside the `['tasks']` prefix, `staleTime: 0` so an edited/deleted task never shows from cache). Meu Perfil has the "Receber e-mails de notificação" switch (`notify_email` via `PATCH /api/profile`; `publicUser` exposes it, `true` by default).

**Env vars.** `APP_URL` (required for notification e-mails; also invite links and the CORS origin), `RESEND_API_KEY`, `EMAIL_FROM` — documented in `.env.example`.

**Rollout order — read `docs/deploy-runbook.md` before deploying.** `supabase db push` applies the RLS lock-down (`20261002`) before the notifications migration (`20261003`), and the lock-down breaks any code that only knows `SUPABASE_ANON_KEY`. Order: (1) set `SUPABASE_SERVICE_ROLE_KEY` and `APP_URL` (plus `RESEND_API_KEY`/`EMAIL_FROM` for e-mail) in Vercel; (2) merge/deploy (the new code works without the notifications table: the bell returns 500 and shows nothing, e-mails are skipped, task saves are unaffected); (3) check login; (4) only then apply both migrations; (5) check again. Rollback after the lock-down needs the old deployment redeployed with `SUPABASE_ANON_KEY` set to the service_role value (or the policies restored).

**Tests.** `tests/notificationRules.test.js` (pure rules), `mailer.test.js` (injected `fetch`), `notifications-service.test.js` (emission, throttle, due materialization), `notifications-api.test.js` (routes, isolation, `GET /api/tasks/:id`), `notificationText.test.js`, `notificationCache.test.js`, `profile-notify.test.js`, `localdb-operators.test.js` (shim `.is()` and `.limit()`).

### Tags
Tasks store tag **names** (`task.tags: string[]`); the registry is `fourbase_tags`. `DELETE /api/tags/:id` is gestor-only, workspace-scoped (404 otherwise), deletes the row and strips the name from every task of the workspace (done in JS so it works on the mock DB too). On the client `useTagActions().deleteTag(tag)` is optimistic (tag list + every cached task list) with rollback; the trash button lives in `TagPicker` rows and is shown only to gestores. Tests: `tests/tags-delete.test.js`.

### Responsive breakpoints
≥1101px: full sidebar. **769–1100px (iPad portrait/landscape): the sidebar is forced into the icon rail** (`compactScreen` in `App.jsx` adds the `collapsed` classes; the toggle is hidden) so content keeps the width — there is no horizontal "sidebar bar" any more. ≤900px: 2-column grids stack (Painel KPIs 2×2, `.dashboard-grid` single column) and the Calendário side panels (mini-calendar+filters, Pendências) stack above/below the grid. ≤768px: compact top bar + sliding drawer (`.mobile-topbar`, `.sidebar.mobile-open`); the desktop `.topbar-actions` are hidden (create "+" and theme live in the mobile bar, refresh in the drawer). `@media (hover: none) and (pointer: coarse)` enlarges touch targets and shows hover-only controls. The final responsive block is at the end of `styles.css`; when adding a screen, check 390, 820 and 1024px.

### Theme (dia/noite)
`src/theme.js` (`fb_theme` in `localStorage`, falls back to `prefers-color-scheme`) sets `<html data-theme="light|dark">`; an inline script in `index.html` applies it before first paint (no flash). All colours come from CSS variables: the dark palette is the `:root[data-theme='dark']` block in `styles.css`. Rules when writing CSS: **surfaces use `var(--surface)` / `var(--surface-2)`, never `var(--white)` or a hardcoded near-white** (`--white` is only for text on coloured buttons, `color: var(--white)`); teal text uses `--primary-text` / `--primary-text-2` (they lighten at night), while `--primary-deep`/`--primary-dark` stay for backgrounds. The sidebar is dark in both themes. Chips with fixed hex colours (priority grayscale, status chips) have dark overrides in the same block.

### Color system
`src/colors.js` exports `assigneeColor(id, overrideColor)` — deterministically hashes an id to a fixed palette color, unless a person/client has picked a custom hex `color` (set via the native `<input type="color">` spectrum picker in `ColorPickerField`, used by `TeamMemberModal`/`ClientModal`). `memberColor(id, list)` is the variant for call sites that only have a foreign key (e.g. `task.assigned_to`) and need to look up the color from a `members`/`clients` array already in scope. This color drives avatars, the Kanban card's left border, and calendar dots — it is deliberately unrelated to task priority, which uses a fixed grayscale scale instead (`.priority-tag.p-*` in `styles.css`).

### Kanban board: layout, filters, sorting
The board (`src/components/Kanban.jsx`) has three parts: a create bar (title always visible; "Opções avançadas" expands every task field: priority, status/column, assignee (gestor), client, start/end date, start/end time, mentioned people, description, tags, image attachments — a counter badge shows how many were touched), the filter bar (`KanbanFilterBar.jsx`) and the columns. **Filters, search and sorting run entirely in the browser** over the tasks already loaded — no API change. All the logic is pure in `src/kanbanFilters.js` (tested in `tests/kanbanFilters.test.js`): within a filter group values are OR, across groups AND; search needs every word (accent/case-insensitive, over title, description and tag names); due buckets are `overdue` (last day passed and **not** in `done`), `today` (today lies between start and end), `week` (starts in 1–7 days), `later`, `none`. `buildFacets` derives each filter's options from the tasks that exist and hides a facet without a real choice (e.g. "Responsável" in the personal Kanban, where `GET /api/tasks` only returns the user's own tasks, so there is a single assignee; "Cliente" in a client board). Filters live in `useState` and start clean on every visit (and per client: `ClientWorkspace` keys the board by `client.id`); only the sort order is remembered (`localStorage` key `fb_kanban_sort`). Never add filtering/sorting back as ad-hoc code in the component — extend `kanbanFilters.js` and its tests.

The create form keeps one `draft` object; its pure logic (initial values, field dependencies — no due date ⇒ no end date/times —, validation messages, the POST body, the badge count) is in `src/newTaskForm.js` (tests: `tests/newTaskForm.test.js`) and mirrors the server rules in `api/_lib/routes/tasks.js`. `Kanban` receives `onAdd(fields)` (the `POST /api/tasks` body) and it must return a promise resolving to the created task or `undefined` on failure: the draft is only cleared on success. Personal board → `createTask`; client board → `createClientTask` with `client_id` pinned to that client. Attachments use `TaskAttachments.jsx` (shared with `TaskDetailModal`) with a provisional id for the Storage path `tasks/<id>/`.

Visual conventions: the card's left stripe is the **assignee's** colour (`--owner`, set inline), priority is the grayscale `.priority-tag` (kept ≥5:1 contrast); small secondary text uses `--muted-strong` (`--muted` is ~4.3:1 on white); interactive elements get `--focus-ring` on `:focus-visible`; transitions use `--ease` and respect `prefers-reduced-motion`. The board uses `.main-wide` (1840px) instead of the global 1200px cap; columns are `flex: 1 1 300px` up to 440px and snap-scroll on phones. Cards are keyboard-focusable (`role="button"`, Enter/Space opens the detail); the move arrows show on hover, on focus and always on touch (`@media (hover: none)`).

### Calendário: grade mensal
`Calendar.jsx` renders each week as its own row: a layer of day cells (click = new task on that date, drop = reschedule) with a 7-column events layer on top (`pointer-events: none`, only the bars capture the mouse; while dragging, `.is-dragging` turns them off so the cell below gets the drop). Placement is pure in `src/calendarLayout.js` (tests: `tests/calendarLayout.test.js`): a multi-day task is **one** bar per week (cut at the week edges, `cont-left`/`cont-right` mark the continuation), single-day items fill the free lanes, at most `MAX_LANES` (3) lanes per day — the rest is a "+N mais" button that opens the day popover. Timed single-day tasks render as dot + time + title (no fill); untimed/multi-day ones are filled with the assignee colour. The tooltip is the native `title` (title, assignee, dates, time). Clicking an empty day opens a quick-create popover (`.calquick`, portal, title only, Enter saves via `createTask` with the date pre-filled; "Mais opções" opens the full `TaskDetailModal` draft carrying the title). "Pendências" (toolbar button with counters) toggles a docked drawer with the "Em atraso" / "Sem data" tabs; items are draggable onto any day or rescheduled with the "Hoje" button — both go through `reschedule(task, date)`, which preserves the duration of multi-day tasks. A docked left panel (toggle: "Filtros" button, remembered in `localStorage` `fb_cal_left`; open by default ≥1100px) holds the `MiniCalendar` (own browsing month, follows the main month when it changes, dots on days with tasks, clicking a day jumps the main calendar there) and checkbox filters for status, assignee and tag with per-option counts. The filter logic is pure in `src/calendarFilters.js` (tests: `tests/calendarFilters.test.js`; same rule as the Kanban — OR within a group, AND across groups, nothing checked = no filter); the text search stays in the toolbar. The old toolbar dropdowns (tags, assignee) and the dead "Fechado" button were removed.

### Kanban columns are data, not constants
Columns (`todo`/`doing`/`done` plus any custom ones) live in `fourbase_columns` (key/label/position/color), not hardcoded in the frontend. `src/columnCache.js` has the `DEFAULT_COLUMNS` fallback + a per-user `localStorage` cache (used by `useColumns`) for the (now rare) case the table has no data yet.

### Painel principal (Dashboard)
Two balanced columns (`.dashboard-col`): upcoming deadlines (checkbox completes via `moveTask(id, 'done')`, overdue rows tinted) + "Agenda de hoje" | progress donut + shortcut cards (Notas has a quick-note "+" → `QuickNoteModal`, which stores escaped HTML via `useNoteActions().addNote`; Kanban "+" opens the create-task modal). Pure logic in `src/dashboardData.js` (`donutSegments`, `todayAgenda`, `quickNoteHtml`; tests in `tests/dashboardData.test.js`). "Criar Tarefa" and "Recarregar dados" live in the desktop `.topbar-actions` (the refresh icon spins while `useIsFetching`); on phones the create "+" is in the mobile top bar and refresh stays in the sidebar drawer (`.action-refresh`). There is no activity-feed data source (no events table), so the "Agenda de hoje" fills that slot.

### Release notes ("O que há de novo")
On login, a step-by-step modal (`WhatsNewModal.jsx`) shows the latest release once per user per browser; the "Novidades" button in the sidebar reopens it. The content is **data**: `src/releaseNotes.js` (`RELEASES`, newest first; user-facing wording, optional `cta` deep link per item). The "seen" rules are pure in `src/whatsNew.js` (`fb_whatsnew_<userId>` in `localStorage`, so it is per browser, not per account; nobody who hasn't finished onboarding sees it — that version is marked as seen). **To publish a version:** add a release at the top of `RELEASES`, mirror it in `CHANGELOG.md`, bump `version` in `package.json` — everyone who hasn't seen that version gets the modal on their next login. Tests: `tests/whatsNew.test.js` (also validates the catalogue shape).

### Icons
`src/icons.jsx` is a hand-rolled SVG icon set (no icon library dependency) built on a shared `Icon` wrapper. Add new icons following that same pattern rather than pulling in a library.

### Deploy
`vercel.json` rewrites `/api/*` to `api/index.js`'s default export, deployed as-is as a serverless function — see the local-mock-DB caveat above before assuming a Vercel preview behaves like local dev.
